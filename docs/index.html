¿Qué es y para qué sirve?

El conector AWS CloudWatch permite que el agente de Ruvic consulte métricas, logs y alarmas de tus recursos en AWS, en modo solo lectura. Una vez configurado, puedes pedirle al agente cosas como:

  • “¿Cómo ha estado el uso de CPU de la instancia i-0abcd1234 en las últimas 6 horas?”
  • “Revisa los logs recientes de la función procesar-pedido para ver si hay errores.”
  • “¿Hay alguna alarma activa en este momento?”

Operaciones soportadas:

Operación Qué hace
cloudwatch.get_metric_statistics Consulta los datapoints de una métrica (ej. uso de CPU, invocaciones)
cloudwatch.get_logs Lee las entradas más recientes de un log group
cloudwatch.list_active_alarms Lista las alarmas que están actualmente en estado ALARM
Solo lectura, por diseño El conector nunca crea, modifica ni elimina métricas, alarmas o logs: solo consulta. Aunque el agente lo intentara, la policy IAM recomendada rechazaría cualquier escritura.

Prerrequisitos

  • Una cuenta de AWS con recursos que ya generen métricas, logs o alarmas en CloudWatch.
  • Acceso a la consola de IAM para crear un usuario y su policy, solo durante la configuración inicial.
  • La región de AWS donde están los recursos a monitorear (ej. us-east-1).

Configuración en el fabricante

Vas a crear un usuario IAM dedicado de solo lectura para Ruvic. No reutilices credenciales root ni las de otra aplicación.

  1. Crea la policy de solo lectura.

    En IAM → Policies → Create policy → pestaña JSON:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "cloudwatch:GetMetricStatistics",
        "cloudwatch:DescribeAlarms"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": ["logs:DescribeLogStreams", "logs:GetLogEvents"],
      "Resource": "arn:aws:logs:*:*:log-group:*:*"
    }
  ]
}
    Nota Para limitar qué logs puede leer el agente, cambia el segundo Resource a un prefijo específico, ej. arn:aws:logs:*:*:log-group:/aws/lambda/ruvic-*:*.
  2. Crea el usuario IAM y adjunta la policy.

    En IAM → Users → Create user → marca "Provide user access to the AWS Management Console" en NO (es un usuario programático) → adjunta la policy del paso 1.

    [ Captura: creación de usuario IAM con la policy adjunta — reemplazar por assets/img/cloudwatch-iam-user.png ]
  3. Genera las claves de acceso.

    En la página del usuario → pestaña "Security credentials" → "Create access key" → tipo "Application running outside AWS". Copia el Access Key ID y el Secret Access Key (este último solo se muestra una vez): los usarás en el formulario de Ruvic.

  4. Verifica el acceso desde la línea de comandos.

    Con el AWS CLI configurado con esas credenciales:

    aws cloudwatch describe-alarms --region us-east-1 --max-records 1

    Si responde sin error (aunque no haya alarmas), el fabricante quedó listo. Anota estos valores para la siguiente sección: Access Key ID, Secret Access Key y región.

Permisos requeridos

Principio de mínimo privilegio: el usuario de Ruvic solo necesita estos permisos, todos de solo lectura. No otorgues cloudwatch:PutMetricAlarm, cloudwatch:DeleteAlarms, cloudwatch:PutMetricData ni logs:PutLogEvents.

Permiso Para qué sirve
cloudwatch:GetMetricStatistics Consultar métricas (cloudwatch.get_metric_statistics)
cloudwatch:DescribeAlarms Listar alarmas activas (cloudwatch.list_active_alarms)
logs:DescribeLogStreams, logs:GetLogEvents (por prefijo de log group) Leer logs recientes (cloudwatch.get_logs)

Configuración en Ruvic

Entra a Settings → Conectores, busca la tarjeta AWS CloudWatch y pulsa Configurar. Diligencia el formulario con los valores que obtuviste en la sección anterior:

Campo del formulario Valor
Access Key ID El Access Key ID del paso 3
Secret Access Key El Secret Access Key del paso 3. Se guarda cifrado como secreto: la interfaz no volverá a mostrarlo
Región de AWS La región donde están los recursos a monitorear (ej. us-east-1)
Timeout de conexión Opcional; 10 segundos por defecto

Guarda y pulsa Probar conexión — la plataforma verificará el acceso a CloudWatch en la región configurada.

[ Captura: formulario del conector AWS CloudWatch en Settings → Conectores — reemplazar por assets/img/cloudwatch-form.png ]

Verificación

  1. Test de conexión exitoso.

    El botón Probar conexión debe responder: “Conexión exitosa a AWS CloudWatch en us-east-1”. La tarjeta del conector cambia a estado Configurado.

  2. Automatización mínima de prueba.

    Abre una conversación nueva con el agente y pídele: “¿Hay alguna alarma activa en CloudWatch en este momento?” El agente debe responder con el listado real de alarmas (o confirmar que no hay ninguna). Si lo hace, el conector quedó operativo de punta a punta.

Solución de problemas

Mensaje / síntoma Causa probable y solución
“Credenciales inválidas o sin permiso IAM suficiente” Access Key o Secret Key mal copiados, o la policy no incluye los permisos necesarios. Reintenta los pasos 1 y 3 de la sección 3.
“No se pudo conectar al servicio CloudWatch … (timeout)” La región configurada no coincide con la región real de los recursos, o hay un problema de red saliente hacia AWS.
get_metric_statistics devuelve una lista vacía No es necesariamente un error: puede significar que no hubo actividad en ese rango de tiempo, o que el namespace/metric_name/dimensions no coinciden con un recurso real. Verifica los nombres exactos en la consola de CloudWatch.
“El log group no existe o no es accesible” Nombre de log group mal escrito (debe incluir la barra inicial, ej. /aws/lambda/mi-funcion), o falta el permiso logs:GetLogEvents sobre ese prefijo. Repite el paso 1 de la sección 3.
El conector aparece “Sin configurar” tras guardar Algún campo obligatorio quedó vacío. Ábrelo de nuevo y completa Access Key ID, Secret Access Key y región.

Preguntas frecuentes y notas de seguridad

¿El agente puede crear o modificar alarmas?

No. El conector nunca llama a PutMetricAlarm, DeleteAlarms ni PutMetricData: solo consulta. El usuario dedicado solo tiene permisos de lectura.

¿Dónde queda guardado el Secret Access Key?

Como secreto en el almacén de credenciales de la plataforma, asociado a tu usuario. La interfaz nunca vuelve a mostrarlo; solo indica “definida”. Para cambiarlo, escribe uno nuevo en el formulario; para conservarlo al editar otros campos, deja el campo vacío.

Rotación de credenciales

Recomendado cada 90 días o según tu política: genera un nuevo Access Key en IAM → Security credentials, actualízalo en el formulario del conector, prueba la conexión, y luego desactiva/elimina la clave anterior desde la consola de AWS.

¿Qué hago si las credenciales se comprometen?

  1. Desactiva o elimina el Access Key de inmediato en IAM → Security credentials.
  2. Revisa la actividad reciente en AWS CloudTrail para ese usuario.
  3. Genera un Access Key nuevo y actualízalo en el formulario del conector.

¿Expiran las credenciales?

Por defecto no (las Access Keys de IAM no expiran solas). Si tu organización exige rotación forzosa, puedes configurar una política de IAM con antigüedad máxima y recibirás alertas para rotarlas manualmente.

Buenas prácticas Usa siempre un usuario IAM dedicado de solo lectura; nunca uses las credenciales root de la cuenta de AWS; restringe el acceso a logs por prefijo si solo necesitas monitorear ciertos recursos; y evita compartir el Secret Access Key por canales no seguros.
